# 02-01 程序内存布局

> demo：[`02_01_memory_layout.cpp`](../../demos/part2_memory/02_01_memory_layout.cpp)

## 一、为什么要懂这个

C++ 把内存管理的控制权交给程序员，代价是你必须知道一个对象"在哪"。
几乎所有 C++ 特有的 bug 都和这件事有关：

- 返回局部变量的引用或地址 → 栈上的对象已经没了
- `delete` 一个栈对象、`delete` 两次、忘记 `delete` → 堆的误用
- 修改字符串字面量 → 写只读段，段错误
- 在栈上开大数组 → 栈溢出
- 静态初始化顺序问题 → 全局区对象的构造时机

这些都不是"记住规则"能解决的，得知道背后的内存模型。

## 二、虚拟内存空间

现在的应用程序都运行在一个虚拟内存空间里。以 32 位系统为例，
寻址空间是 4G，大部分操作系统把其中一部分划给内核，应用程序无法直接访问 ——
这部分叫**内核态空间**。Linux 默认把高地址的 1G 留给内核，
用户使用剩下的 3G，叫**用户态空间**。

64 位系统的地址空间大得多（实际用 48 位，256TB），划分思路一样。

用户态空间的典型区域，从高地址到低地址：

```
高地址
  ┌─────────────────────┐
  │   内核空间（不可访问） │
  ├─────────────────────┤
  │   栈 stack          │  ↓ 向低地址增长
  │        ...          │
  │   （未映射区域）      │
  │        ...          │
  │   mmap 区域         │  大块内存、动态库映射
  │        ...          │
  │   堆 heap           │  ↑ 向高地址增长
  ├─────────────────────┤
  │   .bss  未初始化全局  │
  │   .data 已初始化全局  │
  │   .rodata 只读数据   │
  │   .text 代码         │
  └─────────────────────┘
低地址（32 位下代码段从 0x08048000 开始）
```

五个区域的分工：

1. **栈区（stack）**：由编译器自动分配释放，存放函数参数值、局部变量等。
   操作方式类似数据结构中的栈
2. **堆区（heap）**：一般由程序员分配释放。若程序员不释放，程序结束时由 OS 回收。
   注意它与数据结构中的堆是两回事，分配方式倒是类似链表
3. **全局/静态区**：全局变量和静态变量存储在一起，在程序编译时就确定了布局。
   细分为 `.data`（已初始化）和 `.bss`（未初始化，不占文件体积）
4. **常量区（.rodata）**：存放常量字符串、const 全局量，只读
5. **代码区（.text）**：存放函数体（成员函数、全局函数）的二进制代码

执行一个可执行程序时，加载器把代码和数据从磁盘拷贝到内存。
在段头部表的指导下，可执行文件的内容被放到对应的段里。

## 三、实测各区地址

理论讲完，直接看本机实测（g++ 11.4，x86-64 Linux）：

```
  栈 local                         0x7ffd641e5adc
  栈 str_array                     0x7ffd641e5b01
  栈 &str_literal(指针本身)         0x7ffd641e5ae0

  堆 new int[10]                   0x563cb172aec0
  堆 new int[5]                    0x563cb172aef0
  堆 malloc(64)                    0x563cb172af10

  .bss  g_uninitialized            0x563cb0310154
  .data g_initialized              0x563cb0310010
  .data s_file_scope               0x563cb0310014
  .data s_local(静态局部)           0x563cb0310018

  .rodata g_const                  0x563cb030e008
  .rodata 字符串字面量              0x563cb030e011

  .text some_function              0x563cb030c409
```

读出几个结论：

- **栈在 `0x7ffd...`，远高于其他区域** —— 从最大合法用户地址往下长
- **堆（`0x563cb172...`）比全局区（`0x563cb031...`）高一点** ——
  堆紧跟在读写段之后，向上增长
- **四个段的顺序是 `.text` < `.rodata` < `.data` < `.bss`**，
  地址依次递增，和编译器布局一致
- **静态局部变量 `s_local` 和全局变量在一起**（都在 `.data`），不在栈上。
  这解释了为什么它的值在函数调用之间能保持

### 一个经典的"判断变量在哪个区"的题目

```cpp
int a = 0;              // .data（全局，已初始化）
char* p1;               // .bss （全局，未初始化）

int main() {
    int b;              // 栈
    char s[] = "123456";// s 在栈上，"123456" 的内容被拷贝到栈上的 s 里
    char* p2;           // 栈（指针本身）
    char* p3 = "123456";// p3 在栈上，它指向的 "123456" 在 .rodata
    static int c = 0;   // .data（静态局部）
    p1 = new char[10];  // p1 在 .bss，指向的 10 字节在堆
    p2 = new char[5];   // p2 在栈，指向的 5 字节在堆
    strcpy(p1, "123456");
}
```

`s` 和 `p3` 的区别是最常考的：

```cpp
char s[] = "123456";       // 栈上的数组，内容可改
s[0] = 'X';                // ok

const char* p3 = "123456"; // 指向 .rodata
// p3[0] = 'X';            // 段错误！写只读段
```

C++11 起，字符串字面量的类型是 `const char[N]`，
所以 `char* p = "abc";` 会被拒绝（C++03 下只是废弃）。这个改动正是为了防止上面的错误。

## 四、栈的增长方向

实测：

```
  外层局部变量地址: 0x7ffd641e5b04
  内层局部变量地址: 0x7ffd641e5ae4
  内层地址 更低 -> 栈向低地址增长
```

函数调用越深，栈地址越低。这就是"栈向低地址增长"。

但要注意：**同一作用域内多个变量的相对顺序由编译器决定**：

```
  &a=0x7ffd641e5afc &b=0x7ffd641e5b00 &c=0x7ffd641e5b04
```

这里 `a < b < c`，但换个编译器或优化级别就可能相反。
依赖这个顺序的代码（比如用一个变量的地址去推算另一个）是未定义行为。

### 函数调用时栈上有什么

在函数调用时，第一个进栈的是主调函数中调用语句的下一条指令的地址，
然后是函数的各个参数 —— 在大多数 C 编译器中，参数是**由右往左**入栈的 ——
然后是函数中的局部变量。注意静态变量是不入栈的。

本次函数调用结束后，局部变量先出栈，然后是参数，
最后栈顶指针指向最开始存的返回地址，程序由该点继续运行。

（x86-64 下前六个整型参数实际通过寄存器传递，不入栈。
上面描述的是经典 cdecl 调用约定，理解模型用。）

## 五、堆：申请时发生了什么

操作系统维护一个记录空闲内存的链表。收到程序的申请时，会遍历该链表，
寻找第一个空间大于所申请空间的堆结点，把该结点从空闲链表删除，并分配给程序。

对于大多数系统，**会在这块内存的首地址处记录本次分配的大小** ——
这样 `delete` 语句才能正确释放。所以 `delete` 时不需要你告诉它大小。

由于找到的堆结点大小不一定正好等于申请的大小，系统会把多余的部分重新放入空闲链表。

### 大块内存走的不是 `[heap]`

实测发现一个细节：10MB 的分配落在 `0x7f08429fd010`，
和小块分配的 `0x556829203eb0` 不在同一区域。

查看 `/proc/self/maps` 确认：

```
5568291f2000-556829213000 rw-p 00000000 00:00 0    [heap]
7ffc810af000-7ffc810d0000 rw-p 00000000 00:00 0    [stack]
```

`malloc(100)` 返回 `0x556829203eb0`，落在 `[heap]` 区间内；
`malloc(10MB)` 返回 `0x7f08429fd010`，**不在 `[heap]` 里**。

原因：glibc 的 malloc 对超过阈值（`M_MMAP_THRESHOLD`，默认 128KB）的请求，
直接用 `mmap` 向内核申请独立的匿名映射，而不是从 `brk` 扩展的堆里切。
释放时也直接 `munmap` 还给系统。

这个区别有实际影响：大块内存的分配/释放更慢（要走系统调用），
但不会造成堆碎片，而且释放后立即还给系统（小块内存释放后通常留在进程里复用）。

## 六、栈 vs 堆：六个方面的区别

### 1. 管理方式

- **栈**：由编译器自动管理，无需手工控制
- **堆**：释放工作由程序员控制，容易产生内存泄漏（memory leak）

### 2. 空间大小

- **栈**：有确定的上限，编译/链接时就定了。
  实测本机 `ulimit -s` 是 `8192`（8MB）；Windows 默认 1MB。
  申请超过剩余栈空间就会 overflow
- **堆**：受限于系统的有效虚拟内存，几乎没有实际限制

实测：

```
  char buf[10*1024*1024];        // 很可能 segfault（超过 8MB 栈限制）
  new char[10*1024*1024];        // 成功
```

这是"大对象放堆上"的硬性理由。递归过深导致栈溢出也是同一个限制。

### 3. 分配方式

内存有两种分配方式：静态分配和动态分配。

- **堆**都是动态分配的，没有静态分配的堆
- **栈**既有静态分配（局部变量，由编译器完成）也有动态分配
  （如 C99 的 VLA、`alloca`），但栈的动态分配由编译器负责释放，无需手工处理

### 4. 分配效率

- **栈**由系统自动分配，速度较快，只是移动栈指针（通常一条指令）。但程序员无法控制
- **堆**由 `new` 分配，速度慢得多，要遍历空闲链表、可能加锁、可能走系统调用

实测对比（20 万次 64 字节分配）：

```
  栈: 97 us
  堆: 2507 us
```

**堆分配大约是栈分配的 26 倍耗时**。这个数字解释了很多性能优化手段的由来：
小对象优化（SSO，见 [07-01](../part7_stdlib/07-01_string.md)）、
对象池、`reserve()` 预分配、避免在热循环里 `new`。

### 5. 碎片问题

- **堆**：频繁的 `new`/`delete` 会造成内存空间不连续，产生大量碎片，使程序效率降低
- **栈**：不存在这个问题。因为栈是先进后出的，
  不可能有一个内存块从栈中间弹出 —— 在它弹出之前，在它上面的内容已经先被弹出了

### 6. 增长方向

- **堆**向上增长（向着内存地址增加的方向）
- **栈**向下增长（向着内存地址减小的方向）

### 存储内容的区别

- **栈**：返回地址、函数参数、局部变量
- **堆**：一般在头部用几个字节存放本块的大小，具体内容由程序员安排

## 七、这些知识怎么用

### 判断对象寿命

```cpp
int& bad() { int local = 1; return local; }   // 栈对象，函数返回即销毁
```

知道 `local` 在栈上，就立刻知道这是悬垂引用（见 [01-03](../part1_basics/01-03_reference.md)）。

### 决定对象放哪

| 情况 | 放哪 | 原因 |
|---|---|---|
| 小对象、作用域内用完 | 栈 | 快、自动释放、无碎片 |
| 大对象（> 几十 KB） | 堆 | 栈空间有限 |
| 大小运行时才知道 | 堆 | 栈需要编译期确定（VLA 不是标准 C++）|
| 需要跨作用域存活 | 堆 | 栈对象离开作用域就没了 |
| 多线程共享 | 堆或全局区 | 每个线程有自己的栈 |

### 理解优化手段

- 为什么 `std::string` 要做 SSO —— 短字符串放栈上，省掉 26 倍开销的堆分配
- 为什么 `vector` 要 `reserve` —— 避免反复堆分配 + 元素搬迁
- 为什么要用对象池 —— 把堆分配摊到一次
- 为什么移动语义重要 —— 避免拷贝堆上的数据（见 [02-03](02-03_move_semantics.md)）

### 查看自己程序的段大小

```bash
$ size your_program
   text    data     bss     dec     hex filename
   9366     848     288   10502    2906 your_program
```

`text` 是代码，`data` 是已初始化数据，`bss` 只记录大小不占文件体积。
嵌入式开发里这三个数字要盯着看。

## 八、小结

| 区域 | 存放 | 生命周期 | 大小 |
|---|---|---|---|
| 栈 | 局部变量、参数、返回地址 | 作用域 | 有限（Linux 8MB）|
| 堆 | `new`/`malloc` 的对象 | 手工控制 | 受虚拟内存限制 |
| `.data` | 已初始化全局/静态变量 | 整个程序 | 编译期确定 |
| `.bss` | 未初始化全局/静态变量 | 整个程序 | 编译期确定，不占文件 |
| `.rodata` | 字符串字面量、const 全局量 | 整个程序 | 只读 |
| `.text` | 函数的机器码 | 整个程序 | 只读可执行 |

关键事实：

- 栈向低地址增长，堆向高地址增长，栈的地址远高于堆
- 静态局部变量在全局区，不在栈上
- `char s[] = "x"` 内容在栈（可改），`const char* p = "x"` 内容在 `.rodata`（不可改）
- 堆分配比栈分配慢一个数量级（实测 26 倍）
- 超过 128KB 的分配走 mmap，不在 `[heap]` 区
- 同作用域内变量的地址顺序由编译器决定，不可依赖
