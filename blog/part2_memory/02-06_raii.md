# 02-06 RAII 与资源管理惯用法

> demo：[`02_06_raii.cpp`](../../demos/part2_memory/02_06_raii.cpp)

## 一、RAII 是什么

**RAII（Resource Acquisition Is Initialization，资源获取即初始化）**：
把资源的生命周期绑定到对象的生命周期上 ——
构造函数获取资源，析构函数释放资源。

名字起得不好。它强调的是"获取"，而真正的价值在"释放" ——
更准确的叫法应该是"**析构函数负责释放**"。

它能工作的基础是 C++ 的两条保证：

1. **栈对象离开作用域时，析构函数一定被调用**
2. **异常传播时的栈展开，会逆序析构所有已构造的局部对象**
   （见 [01-08](../part1_basics/01-08_exception.md)）

把这两条合起来：**只要资源由栈对象管理，它就一定会被释放** ——
无论函数是正常返回、提前 return、还是抛了异常。

这是 C++ 相对于 C 最重要的工程优势，也是 C++ 不需要 `finally` 语句的原因
（Java/C# 需要 `try-finally`，Go 需要 `defer`，Python 需要 `with`，
C++ 把这件事交给了类型系统）。

## 二、最小实现

```cpp
class FileHandle {
public:
    // 1. 构造函数获取资源，失败就抛异常
    explicit FileHandle(const char* path, const char* mode)
        : _fp(std::fopen(path, mode)) {
        if (!_fp) throw std::runtime_error("无法打开文件");
    }

    // 2. 析构函数释放资源
    ~FileHandle() {
        if (_fp) std::fclose(_fp);
    }

    // 3. 禁止拷贝（句柄不能被复制，否则会 double close）
    FileHandle(const FileHandle&) = delete;
    FileHandle& operator=(const FileHandle&) = delete;

    // 4. 支持移动（表达所有权转移）
    FileHandle(FileHandle&& rhs) noexcept : _fp(rhs._fp) { rhs._fp = nullptr; }
    FileHandle& operator=(FileHandle&& rhs) noexcept {
        if (this != &rhs) {
            if (_fp) std::fclose(_fp);
            _fp = rhs._fp;
            rhs._fp = nullptr;
        }
        return *this;
    }

    void write(const char* s) { std::fputs(s, _fp); }
private:
    std::FILE* _fp;
};
```

用起来：

```cpp
try {
    FileHandle f("/tmp/demo.txt", "w");
    f.write("data");
    throw std::runtime_error("中途抛异常");
}  catch (...) { /* ... */ }
```

实测输出证明文件在异常传播前就关闭了：

```
      获取文件句柄
      释放文件句柄
      捕获: 中途抛异常（但文件已经关闭了）
```

### RAII 类的四条要素

1. **构造函数获取资源，失败就抛异常** ——
   这样"对象存在"就等价于"资源有效"，不需要在每次使用前检查
2. **析构函数释放资源，且绝不抛异常** —— 原因见第六节
3. **禁止拷贝，或者实现正确的深拷贝** ——
   默认的浅拷贝会导致同一个资源被释放两次
4. **通常支持移动** —— 让所有权可以转移，这样对象能从函数返回、放进容器

第 3、4 条合起来就是 [02-03](02-03_move_semantics.md) 讲的 Rule of Five。

## 三、标准库里的 RAII 类型

不需要自己写，标准库已经把常见资源包好了：

| 类型 | 管理的资源 |
|---|---|
| `std::string` / `std::vector` | 堆内存 |
| `std::unique_ptr` / `std::shared_ptr` | 任意资源（配自定义删除器）|
| `std::fstream` / `ifstream` / `ofstream` | 文件句柄 |
| `std::lock_guard` / `unique_lock` / `scoped_lock` | 互斥量 |
| `std::thread`（C++20 `jthread`） | 线程 |

```cpp
{
    std::ofstream ofs("/tmp/demo.txt");
    ofs << "data";
}   // 析构时自动 close

std::mutex mtx;
{
    std::lock_guard<std::mutex> lk(mtx);   // 构造时 lock
    // 临界区，即使抛异常也保证解锁
}   // 析构时 unlock
```

实测确认：

```
      fstream 已自动关闭
      lock_guard 持锁期间
      lock_guard 已自动解锁
```

`lock_guard` 是 RAII 价值最明显的例子。手工管锁的代码：

```cpp
mtx.lock();
if (condition) return;      // 忘了 unlock -> 死锁
do_work();                  // 抛异常 -> 死锁
mtx.unlock();
```

死锁比内存泄漏更难查 —— 程序不崩溃，只是卡住。
`lock_guard` 让这类 bug 从源头消失。详见 [08-02](../part8_concurrency/08-02_mutex.md)。

## 四、scope guard：给没有 RAII 封装的资源临时加一层

有时资源来自 C 库，只有 `acquire`/`release` 两个函数，
为它专门写一个 RAII 类又太重。这时用 **scope guard**：
一个在析构时执行任意可调用对象的小工具。

```cpp
template <class F>
class ScopeGuard {
public:
    explicit ScopeGuard(F f) : _f(std::move(f)), _active(true) {}
    ~ScopeGuard() { if (_active) _f(); }

    void dismiss() { _active = false; }       // 主动放弃执行

    ScopeGuard(const ScopeGuard&) = delete;
    ScopeGuard& operator=(const ScopeGuard&) = delete;
    ScopeGuard(ScopeGuard&& rhs) noexcept
        : _f(std::move(rhs._f)), _active(rhs._active) { rhs._active = false; }
private:
    F _f;
    bool _active;
};

template <class F>
ScopeGuard<F> make_guard(F f) { return ScopeGuard<F>(std::move(f)); }
```

（C++17 有了 CTAD 之后，`ScopeGuard guard{[]{...}};` 可以直接写，
不再需要 `make_guard`，见 [05-02](../part5_template/05-02_class_template.md)。）

### 包装 C API

```cpp
void* handle = c_acquire();
auto guard = make_guard([handle] { c_release(handle); });

// 中间可以随意 return 或抛异常，c_release 一定会被调用
```

实测：

```
      c_acquire()
      使用 handle，中间可以随意 return 或抛异常
      c_release()
```

这相当于 Go 的 `defer`，但比 `defer` 更精确 ——
`defer` 在函数结束时执行，scope guard 在**作用域**结束时执行。

### dismiss：用于事务回滚

`dismiss()` 让 scope guard 能表达"失败就回滚，成功就不回滚"：

```cpp
auto rollback = make_guard([&] { undo_changes(); });

do_step1();
do_step2();      // 任何一步抛异常，rollback 自动执行

rollback.dismiss();   // 全部成功，取消回滚
```

实测：

```
    dismiss 取消清理（事务提交成功的场合）:
      执行事务...成功
      （没有回滚输出，因为已 dismiss）
```

这个模式在数据库操作、文件批量改名、多步状态机里都很有用。

> 标准化状态：`scope_exit` / `scope_fail` / `scope_success`
> 在 Library Fundamentals TS v3 里，尚未进入标准。
> 实践中可以用上面这个 20 行的实现，或者 Boost.ScopeExit、GSL 的 `finally`。

## 五、copy-and-swap：实现强异常安全

RAII 保证了"不泄漏"（基本保证）。要做到"**要么全成功，要么状态完全不变**"
（强保证），需要另一个惯用法。

问题出在多步操作上：

```cpp
void Config::update_unsafe(const std::string& k, const std::string& v) {
    _keys.push_back(k);       // 如果下一行抛异常……
    _values.push_back(v);     // _keys 已经改了，两个容器长度不一致
}
```

对象进入了不一致状态 —— 没泄漏资源，但数据已经坏了。

**copy-and-swap**：在副本上完成所有可能失败的操作，
最后用不抛异常的 `swap` 一次性生效：

```cpp
void Config::update_safe(const std::string& k, const std::string& v) {
    auto new_keys = _keys;          // 可能抛异常，但只影响副本
    auto new_values = _values;
    new_keys.push_back(k);
    new_values.push_back(v);

    _keys.swap(new_keys);           // swap 不抛异常
    _values.swap(new_values);       // 这两步构成"提交"
}
```

实测：

```
      update_safe 两次后 size=2 一致=1
```

要点：**`swap` 必须是 `noexcept` 的**。标准容器的 `swap` 只交换内部指针，
满足这个要求。这就是"提交点不能失败"的实现方式。

代价是一次完整的拷贝。所以强保证不是免费的 ——
要根据场景决定是否值得（配置更新值得，热路径上的高频操作通常不值得）。

copy-and-swap 还能用来实现赋值运算符：

```cpp
Widget& operator=(Widget rhs) {    // 注意：按值传参，拷贝在这里发生
    swap(*this, rhs);               // 交换后，rhs 带着旧数据离开并析构
    return *this;
}
```

这一个函数同时实现了拷贝赋值和移动赋值（传左值时拷贝构造参数，
传右值时移动构造参数），而且天然处理自赋值、天然强异常安全。
详见 [03-04](../part3_class/03-04_copy_control.md)。

## 六、为什么析构函数绝不能抛异常

RAII 把释放逻辑放进析构函数，而析构函数会在栈展开期间被调用。
如果此时它再抛一个异常，就有两个异常同时在传播 ——
C++ 没有处理这种情况的机制，运行时直接 `std::terminate`。

C++11 起**析构函数默认是 `noexcept`**，想抛必须显式写 `noexcept(false)`。
语言在用默认值阻止你犯这个错。

那清理动作本身可能失败怎么办？比如关文件时 flush 失败。
标准做法是**双接口**：

```cpp
class FileWriter {
public:
    // 显式关闭：调用方可以处理错误
    void close() {
        if (_fp && std::fclose(_fp) != 0) throw std::runtime_error("flush 失败");
        _fp = nullptr;
    }

    // 析构：吞掉异常，保证不逃出
    ~FileWriter() {
        if (_fp) {
            try { std::fclose(_fp); } catch (...) { /* 记日志，不抛 */ }
        }
    }
};
```

`std::fstream` 就是这么设计的：既有析构函数自动关闭（兜底），
也有 `close()` 供需要检查错误的调用方使用。

## 七、RAII 的边界

RAII 不是万能的，有几类情况它处理不了或不方便。

**一、生命周期不由作用域决定。** 比如对象要在多个线程间共享、
或者寿命由运行时逻辑决定。这时用 `shared_ptr`（把"何时释放"交给引用计数）。

**二、资源需要在构造后才能确定。** 构造函数获取资源的模式要求
"构造时资源就绪"。延迟初始化可以用 `std::optional`
（见 [07-04](../part7_stdlib/07-04_tuple_variant.md)）：

```cpp
std::optional<FileHandle> maybe_file;      // 还没获取资源
if (need_file) maybe_file.emplace(path, "w");   // 这时才获取
```

**三、跨 ABI 边界。** 动态库接口、C 接口不能传 RAII 对象，
只能传裸句柄，然后在边界两侧各自用 RAII 包装。

**四、构造函数失败的报告。** 构造函数只能通过异常报错。
禁用异常的环境（嵌入式、部分游戏引擎）里，
RAII 类通常改成"构造函数不做事 + `init()` 返回错误码"，
这就牺牲了"对象存在即资源有效"的保证。

## 八、小结

| 要点 | 说明 |
|---|---|
| 核心机制 | 构造函数获取资源，**析构函数释放资源** |
| 为什么可靠 | 栈对象的析构函数一定被调用，包括栈展开期间 |
| 四条要素 | 构造获取（失败抛异常）、析构释放（不抛异常）、禁拷贝或深拷贝、支持移动 |
| 标准库已有 | `string`/`vector`/`unique_ptr`/`fstream`/`lock_guard`/`thread` |
| scope guard | 给只有 `acquire`/`release` 的 C API 临时加一层；`dismiss()` 支持事务回滚 |
| copy-and-swap | 在副本上操作 + `noexcept` 的 swap 提交 = 强异常安全 |
| 析构函数 | 默认 `noexcept`；需要报错时另外提供显式 `close()` |
| 边界 | 寿命跨作用域用 `shared_ptr`；延迟获取用 `optional`；ABI 边界只能传句柄 |

一句话总结整个 Part 2：**不要手工管理资源**。
内存用 `vector`/`string`/智能指针，锁用 `lock_guard`，文件用 `fstream`，
其他资源用 `unique_ptr` 配自定义删除器或 scope guard。
手写 `new`/`delete`、`lock`/`unlock`、`open`/`close` 配对的代码，
在现代 C++ 里都应该被视为需要重构的信号。
