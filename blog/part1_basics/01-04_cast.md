# 01-04 类型转换

> 标准：C++98（四种 cast）
> demo：[`01_04_cast.cpp`](../../demos/part1_basics/01_04_cast.cpp)

## 一、解决了什么问题

C 风格的类型转换语法很简单：

```c
TYPE a = (TYPE) EXPRESSION;
```

简单到有害。它的问题有两个。

**第一，一种语法干了四件危险程度完全不同的事。** 看这四行：

```cpp
double d1  = (double)ci;        // 数值转换，安全
int* p1    = (int*)&ci;         // 悄悄去掉了 const
Derived* p2 = (Derived*)pb;     // 向下转型，无任何检查
auto addr  = (uintptr_t)pb;     // 重新解释比特位
```

语法上**完全看不出区别**。把一个指向 const 对象的指针转成非 const 指针，
和把基类指针转成派生类指针，这两种转换的差别是巨大的，
但传统 C 风格的类型转换没有区分它们。读代码的人无法判断某个 `(T)x`
是无害的数值转换，还是正在拆掉类型系统的保险。

**第二，找不到。** C 风格转换由一个括号加一个标识符组成，
而这样的东西在 C++ 程序里一大堆 —— 函数调用、表达式分组、构造函数调用，全都长这样。
想审查"这个项目里所有危险的转换"，`grep` 无从下手。

C++ 为此引入了四个转换运算符：`static_cast`、`const_cast`、`dynamic_cast`、
`reinterpret_cast`。它们把"你到底想做哪种转换"写进了代码，
编译器因此能拒绝不合理的组合，而且全都可以 grep 到。

## 二、static_cast：正常情况下的转换

最常用的一个，用于"合理且编译期可验证"的转换。

```cpp
int iNumber = 100;
float fNumber = static_cast<float>(iNumber);

double d = 3.99;
int truncated = static_cast<int>(d);          // 3，显式表达"我知道会截断"

void* pvoid = std::malloc(sizeof(int));
int* pInt = static_cast<int*>(pvoid);         // void* -> 具体类型
```

它的用途归纳为五类：

1. 基本数据类型之间的转换（`int` ↔ `char`、`int` ↔ `enum`、整型 ↔ 浮点）。
   **安全性由开发人员保证** —— 编译器只负责确认这种转换"存在"，不保证值不丢失
2. `void*` 转成目标类型的指针
3. 把任何类型的表达式转换成 `void` 类型（抑制"未使用变量"警告的标准手法）
4. 类层次结构中基类和派生类之间的指针或引用转换
5. 调用显式构造函数或转换运算符

它**做不到**的事情同样重要 —— 无关类型的指针之间不能转：

```cpp
int x = 1;
int* px = &x;
// float* pf = static_cast<float*>(px);   // 编译错误：invalid static_cast
```

这正是它比 C 风格安全的地方：真正危险的重新解释，被挡在了编译期。

### 类层次中的 static_cast：上行安全，下行不安全

```cpp
Derived d;
Base* pb = static_cast<Base*>(&d);        // 上行转换（派生 -> 基类）：永远安全
Derived* pd = static_cast<Derived*>(pb);  // 下行转换（基类 -> 派生）：不做检查
```

**上行转换**（把派生类的指针或引用转换成基类表示）是安全的 ——
派生类对象里确实包含一个基类子对象。这类转换通常连 cast 都不用写，是隐式的。

**下行转换**（把基类指针或引用转换成派生类）**不安全**，因为没有动态类型检查。
如果对象的真实类型不是目标类型，编译器不会阻止你：

```cpp
Other o;                   // Other 和 Derived 是兄弟类
Base* pbo = &o;
Derived* wrong = static_cast<Derived*>(pbo);   // 编译通过！
// wrong->derived_only();  // 未定义行为
```

实测输出：

```
static_cast 把 Other* 当成 Derived*，编译器没有阻止：0x7fff597469d0
```

拿到了一个看起来有效的指针，用它就是未定义行为。需要检查的下行转换，用 `dynamic_cast`。

## 三、dynamic_cast：带运行期检查的下行转换

`dynamic_cast` 主要用于基类和派生类之间的转换，**尤其是向下转型**。
它在运行期检查对象的真实类型，失败时给出明确结果而不是未定义行为。

```cpp
for (Base* pb : targets) {
    if (Derived* pd = dynamic_cast<Derived*>(pb)) {   // 失败返回 nullptr
        pd->derived_only();
    } else {
        // 安全地处理"不是这个类型"的情况
    }
}
```

实测输出：

```
实际类型 Derived: dynamic_cast 成功 ->   只有 Derived 才有的方法
实际类型 Other: dynamic_cast 返回 nullptr（安全地失败了）
```

指针版本和引用版本的失败行为不同：

| 形式 | 失败时 |
|---|---|
| `dynamic_cast<Derived*>(pb)` | 返回 `nullptr` |
| `dynamic_cast<Derived&>(rb)` | 抛出 `std::bad_cast` |

引用没有"空引用"，所以只能抛异常：

```cpp
try {
    Derived& rd = dynamic_cast<Derived&>(rb);
} catch (const std::bad_cast& e) {
    std::cout << e.what();   // std::bad_cast
}
```

### 使用前提与代价

`dynamic_cast` 依赖 **RTTI（运行期类型信息）**，因此：

- **基类必须有虚函数**（至少一个，通常是虚析构函数），否则编译错误。
  因为 RTTI 信息是通过虚表指针找到的，没有虚表就无从查询
- 需要编译器开启 RTTI。有些嵌入式项目用 `-fno-rtti` 关掉它来省空间，
  那里 `dynamic_cast` 和 `typeid` 都不可用
- 有运行期开销：需要遍历继承关系做比较，比 `static_cast`（零开销）慢得多

相关的还有 `typeid`，用于直接查询类型：

```cpp
Base* pb = &d;
typeid(*pb).name();   // 实测输出 "7Derived"（GCC 的 mangled name，7 是名字长度）
```

`typeid(*pb)` 给的是**真实类型**，而 `typeid(pb)` 给的是静态类型 `Base*`。
`name()` 的返回值格式由实现定义，要可读的名字需要用 `abi::__cxa_demangle`。

### 频繁使用 dynamic_cast 通常是设计信号

```cpp
// 气味：用类型判断代替多态
if (auto* d = dynamic_cast<Dog*>(animal))      d->bark();
else if (auto* c = dynamic_cast<Cat*>(animal)) c->meow();

// 通常应该改成：
animal->make_sound();      // 虚函数
```

正当用途是那些无法用虚函数表达的场合：从异构容器里挑出特定类型、
实现序列化/反序列化、插件系统里的接口查询（类似 COM 的 `QueryInterface`）。

## 四、const_cast：增删 const 属性

它只能修改类型的 const（和 volatile）属性：常量指针被转成非常量指针，
并且**仍然指向原来的对象**；常量引用被转成非常量引用，同样指向原对象。

```cpp
const int number = 100;
// int* bad = &number;                    // 编译错误
int* p = const_cast<int*>(&number);       // 编译通过
// *p = 200;                              // 未定义行为！
```

这里有个关键区分，很多人会搞错：

**`const_cast` 本身是合法的，但通过它修改一个"真正的 const 对象"是未定义行为。**

```cpp
// UB：number 本身就是 const 对象，编译器可能把它放进只读段，或直接内联它的值
const int number = 100;
*const_cast<int*>(&number) = 200;

// 合法：real 本身不是 const，只是手里的指针带了 const
int real = 10;
const int* cp = &real;
*const_cast<int*>(cp) = 20;     // real 变成 20
```

实测输出：

```
const_cast 之后指针有效，*p = 100
对非 const 对象去 const 后修改: real = 20
```

所以 `const_cast` 的正当用途只有两类：

1. **对象本身不是 const，只是当前拿到的指针/引用带了 const**
2. **对接 const 正确性不完善的老接口**（典型是只收 `char*` 但实际不修改的 C API）

```cpp
void legacy_c_api(char* buf);              // 老接口，其实不改 buf
std::string s = "hello";
legacy_c_api(const_cast<char*>(s.c_str()));
```

如果你在自己的代码里需要 `const_cast` 来修改成员，那是设计问题 —— 应该用 `mutable`
（见 [01-02](01-02_const_constexpr.md)）或者重新考虑这个函数是否该是 const。

## 五、reinterpret_cast：重新解释比特位

它用来处理无关类型之间的转换：任意指针（或引用）类型之间的转换，
以及指针与足够大的整数类型之间的转换。它的效果很强大，
但错误使用极易导致程序不安全。

**唯一完全安全的用法是"往返"**：转换出去再转换回原始类型。

```cpp
int x = 42;
int* px = &x;
auto addr = reinterpret_cast<std::uintptr_t>(px);   // 指针 -> 整数
int* back = reinterpret_cast<int*>(addr);           // 整数 -> 指针
*back;   // 42，安全
```

另一个常见的正当用法是按字节查看对象表示（`unsigned char*`/`std::byte*`
被标准特许可以别名任何对象）：

```cpp
float f = 1.0f;
auto* bytes = reinterpret_cast<unsigned char*>(&f);
for (std::size_t i = 0; i < sizeof(f); ++i) { /* 打印 bytes[i] */ }
```

实测输出（小端机器上的 IEEE-754 单精度 1.0f）：

```
float 1.0f 的字节: 0 0 80 3f
```

**危险用法：类型双关（type punning）**

```cpp
int x = 42;
float* pf = reinterpret_cast<float*>(&x);
std::cout << *pf;     // 未定义行为：违反严格别名规则
```

编译器假定不同类型的指针不会指向同一块内存（严格别名规则），
在 `-O2` 下这类代码可能被优化成任何结果。要做类型双关，正确方式是：

```cpp
float f;
std::memcpy(&f, &x, sizeof(f));       // 任何标准都合法，编译器会优化掉 memcpy
// 或者 C++20: auto f = std::bit_cast<float>(x);
```

`reinterpret_cast` 的典型场合是底层代码：网络字节流解析、
设备寄存器映射、内存池、与 C 结构体互操作。应用层代码里出现它，通常值得质疑。

## 六、四种 cast 对照

| cast | 检查时机 | 典型用途 | 危险程度 |
|---|---|---|---|
| `static_cast` | 编译期 | 数值转换、`void*` 还原、上行转换、显式构造 | 低（下行转换时中等）|
| `dynamic_cast` | **运行期** | 安全的下行转换、接口查询 | 低（失败可检测），但有开销 |
| `const_cast` | 编译期 | 去掉多余的 const、对接老 C 接口 | 中（改真 const 对象是 UB）|
| `reinterpret_cast` | 几乎不检查 | 指针↔整数、按字节访问 | **高** |

选择顺序：

1. 能不转换就不转换 —— 很多转换是设计问题的症状
2. 需要转换时，从 `static_cast` 开始
3. 需要运行期检查的下行转换，用 `dynamic_cast`
4. 只有在确实要去 const 时用 `const_cast`
5. `reinterpret_cast` 留给底层代码，并写注释说明为什么安全
6. **永远不要用 C 风格转换**（唯一例外是必须兼容 C 编译器的头文件）

## 七、小结

- C 风格转换的两个根本问题：**一种语法混淆四种语义**、**无法检索**
- `static_cast` 是默认选择，编译期可验证；下行转换时它不做检查
- `dynamic_cast` 是唯一带运行期检查的，要求基类有虚函数，有开销
- `const_cast` 合法，但修改真 const 对象是 UB
- `reinterpret_cast` 只在"往返"和"按字节访问"时安全，类型双关请用 `memcpy`
- 频繁需要 cast（尤其 `dynamic_cast`）通常意味着设计需要调整
