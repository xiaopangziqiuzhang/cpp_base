# 04-07 多态的代价与 CRTP

> demo：[`04_07_crtp.cpp`](../../demos/part4_oop/04_07_crtp.cpp)

前面六章讲的都是"怎么用虚函数"。这一章讲它的**代价**，
以及什么时候应该换一种做法。

## 一、虚函数的三项代价

### 代价一：对象变大

每个对象多一个虚表指针。实测：

```
        sizeof(dynamic_poly::Circle) = 16（double + 虚表指针）
        sizeof(static_poly::Circle)  = 8（只有 double，空基类优化）
```

一个只含 `double` 的类，加上虚函数后从 8 字节变成 16 字节 —— 翻倍。
对于要存几百万个的小对象，这个差别直接影响内存占用和缓存命中率。

### 代价二：调用多一次间接跳转

```cpp
p->area();
// 虚调用：  取 vptr -> 查虚表槽位 -> 间接跳转
// 非虚调用：直接跳转（或内联，完全没有跳转）
```

间接跳转本身只是几个时钟周期，但它对 CPU 的**分支预测**不友好 ——
目标地址要等到运行时才知道。如果一个循环里交替调用不同派生类的实现，
间接跳转的目标反复变化，预测失败的代价（流水线清空，十几个周期）会累积起来。

### 代价三：无法内联（最重要的一项）

这是三项中影响最大的。编译器在编译 `p->area()` 时不知道实际类型，
所以**无法内联这个调用**。

内联的价值远不止"省掉函数调用开销"。内联之后，编译器能看到调用点的上下文，
可以做常量传播、公共子表达式消除、循环向量化 ——
这些优化在跨函数边界时都做不到。

`area()` 这种函数体只有一次乘法的函数，内联后开销近乎为零，
不内联则要付出完整的函数调用成本。**对小函数来说，不能内联意味着几倍的差距。**

### 实测

同样 200 万次 `area()` 调用：

```
# -O0（本书构建脚本的默认配置）
        动态多态（虚函数）: 63254 us
        静态多态（CRTP）  : 18059 us

# -O2（更有意义的对比）
        动态多态（虚函数）: 6434 us
        静态多态（CRTP）  : 1604 us
```

`-O2` 下仍有约 **4 倍**差距。

但要诚实地说明这个对比的局限：

1. 动态版本的元素分散在堆上（`vector<unique_ptr<Shape>>`），
   静态版本是连续数组 —— **缓存局部性也不同**，这部分差距不该算在虚函数头上
2. 实际项目里的函数体通常比 `area()` 大得多，
   函数调用开销占比下降，差距会显著缩小

所以这个数字的意义是"说明虚调用有实质代价"，**不是**"虚函数慢 4 倍"。
真实场景里的差距通常小得多，而且往往完全不重要。

### 什么时候这些代价才值得关心

**大多数时候不值得。** 虚函数的开销在以下情况才成为问题：

- 函数体很小（几行以内），调用开销占比高
- 调用极其频繁（每秒百万次以上）
- 在紧凑的循环里，阻止了向量化
- 对象数量巨大，多一个指针的内存开销可观

如果你的虚函数里有一次 IO、一次分配、或者几十行计算，
那虚调用的开销完全可以忽略。**先测量，再优化。**

## 二、去虚化：编译器也在帮忙

现代编译器会尝试**去虚化（devirtualization）**，
在能确定实际类型时把虚调用变成直接调用：

```cpp
Circle c;
c.area();              // 通过对象调用，类型确定 -> 去虚化 + 内联

void f(const FinalDerived& d) { d.area(); }   // final 类 -> 可以去虚化

std::unique_ptr<Shape> p = std::make_unique<Circle>(1.0);
p->area();             // 编译器能追踪到 p 的实际类型 -> 可能去虚化
```

帮助编译器去虚化的手段：

- 用 `final` 标记类或虚函数（见 [04-05](04-05_override.md)）
- 开启 **LTO**（`-flto`）—— 让编译器看到整个程序，
  如果某个虚函数只有一个实现，就可以直接调用
- 把虚函数调用移出热循环

## 三、CRTP：编译期的多态

**CRTP（Curiously Recurring Template Pattern，奇异递归模板模式）**：
基类模板以派生类自己作为模板参数。

```cpp
template <class Derived>
class Shape {
public:
    // 非虚函数，但能调用派生类的实现
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }

    // 也可以提供默认实现
    std::string describe() const {
        return "面积 = " + std::to_string(area());
    }
};

class Circle : public Shape<Circle> {        // 把自己传给基类
public:
    double area_impl() const { return 3.14159 * _r * _r; }
private:
    double _r;
};
```

关键在 `static_cast<const Derived*>(this)` ——
基类知道自己的派生类是谁，所以可以**静态地**转换过去调用具体实现。
这个转换在编译期完成，没有运行期开销，而且调用可以内联。

### 为什么这是合法的

看起来很奇怪：`Shape<Circle>` 在定义时 `Circle` 还不完整。
但这没问题，因为**模板的成员函数体直到被调用时才实例化** ——
那时 `Circle` 已经是完整类型了。

这也是 CRTP 的一个约束：基类**不能在自己的类体内**使用
`Derived` 的任何成员（比如 `sizeof(Derived)` 或 `typename Derived::value_type`），
只能在成员函数体里用。

### 效果

```
        sizeof(static_poly::Circle) = 8    <- 没有虚表指针
```

对象大小不变（基类是空的，被空基类优化掉了，见 [04-01](04-01_inheritance.md)），
调用可以内联。

## 四、CRTP 的典型用途

CRTP 的价值不只是性能。它真正独特的能力是**给一批类注入通用实现**。

### 用途一：混入运算符（mixin）

从 `operator<` 自动派生出其余比较运算符：

```cpp
template <class Derived>
class Comparable {
public:
    friend bool operator>(const Derived& a, const Derived& b)  { return b < a; }
    friend bool operator<=(const Derived& a, const Derived& b) { return !(b < a); }
    friend bool operator>=(const Derived& a, const Derived& b) { return !(a < b); }
    friend bool operator==(const Derived& a, const Derived& b) {
        return !(a < b) && !(b < a);
    }
    friend bool operator!=(const Derived& a, const Derived& b) {
        return (a < b) || (b < a);
    }
};

class Version : public Comparable<Version> {
public:
    friend bool operator<(const Version& a, const Version& b) { /* ... */ }
};
```

实测：

```
        1.2 < 1.5 : 1
        1.2 > 1.5 : 0
        1.2 <= 1.5 : 1
        1.2 == 1.5 : 0
      只写了 operator<，其余 5 个由 CRTP 基类生成
```

用虚函数做不到这件事 —— 虚函数的返回类型和参数类型是固定的，
而这里每个派生类需要的是**自己类型**的运算符。

（注：C++20 的三路比较运算符 `<=>` 让这个特定用法基本不再必要，
但 CRTP 混入的思路仍然有效。Boost.Operators 库是这个模式的经典实现。）

### 用途二：每个派生类独立的静态成员

```cpp
template <class Derived>
class Counted {
public:
    Counted() { ++_count; }
    ~Counted() { --_count; }
    static int count() { return _count; }
private:
    static inline int _count = 0;      // [C++17]
};

class Widget : public Counted<Widget> {};
class Gadget : public Counted<Gadget> {};
```

实测：

```
        Widget::count() = 3
        Gadget::count() = 1
```

因为 `Counted<Widget>` 和 `Counted<Gadget>` 是**两个不同的类型**，
各有一份独立的静态成员。用普通继承（`class Widget : public Counted`）
就只有一个共享的计数器。

这是 CRTP 独有的能力 —— 模板参数化让每个派生类得到一份"专属"的基类。

### 用途三：标准库里的例子

```cpp
// std::enable_shared_from_this 就是 CRTP
class Widget : public std::enable_shared_from_this<Widget> {
public:
    std::shared_ptr<Widget> self() { return shared_from_this(); }
    //                              ^ 返回 shared_ptr<Widget>，不是 shared_ptr<void>
};
```

正是因为 CRTP，`shared_from_this()` 才能返回**精确类型**的
`shared_ptr`（见 [02-05](../part2_memory/02-05_smart_pointers.md)）。

其他例子：`std::iterator`（已废弃）、Boost.Iterator 的
`iterator_facade`、Eigen 的表达式模板、各种 `singleton<T>` 实现。

## 五、CRTP 的代价

CRTP 不是"免费的虚函数"，它有自己的问题。

**一、无法做异构容器。** 这是最根本的限制：

```cpp
// 动态多态：可以
std::vector<std::unique_ptr<Shape>> shapes;      // 存各种形状

// CRTP：做不到
// std::vector<???> shapes;    // Shape<Circle> 和 Shape<Square> 是不同类型
```

CRTP 的每个派生类有不同的基类类型，没有共同的基类可以用来存放它们。
需要异构容器时，要么回到虚函数，要么用 `std::variant`
（见 [07-04](../part7_stdlib/07-04_tuple_variant.md)）。

**二、代码膨胀。** 每个 `Derived` 实例化一份基类代码。
10 个派生类就有 10 份 `describe()` 的代码。虚函数只有一份。

**三、编译变慢，错误信息难读。** 模板的通病。
一个 CRTP 的类型错误可能产出几百行错误信息。

**四、必须在编译期知道类型。** 插件系统、从配置文件决定类型、
从网络数据决定类型 —— 这些场合 CRTP 完全用不上。

**五、跨 ABI 边界不可用。** 模板代码必须在头文件里，
无法像虚函数那样提供稳定的二进制接口。

## 六、怎么选

| 需求 | 选择 |
|---|---|
| 运行期才知道类型（插件、配置、用户输入）| **虚函数** |
| 需要异构容器（`vector<Base*>`）| **虚函数** |
| 跨动态库的接口（ABI 稳定）| **虚函数** |
| 类型多且经常变化 | **虚函数** |
| 编译期已知类型 + 性能关键 | **CRTP / 模板** |
| 给一批类注入通用实现（mixin）| **CRTP** |
| 每个派生类需要独立的静态成员 | **CRTP** |
| 需要精确的派生类型（如 `shared_from_this`）| **CRTP** |

### 还有第三条路：不用继承

很多情况下两者都不需要：

```cpp
// 用 std::function：运行期多态，但不需要继承
std::vector<std::function<double()>> area_calculators;

// 用 std::variant：闭集合的多态，无虚函数开销
using Shape = std::variant<Circle, Square, Triangle>;
std::vector<Shape> shapes;
double area = std::visit([](const auto& s) { return s.area(); }, shapes[0]);

// 用模板 + 鸭子类型：最简单
template <class Shape>
double total_area(const std::vector<Shape>& shapes) { /* ... */ }
```

`std::variant` 特别值得考虑 ——
当"所有可能的类型"是一个**已知的、封闭的集合**时，
它比虚函数更快（无间接跳转）、更安全（`std::visit` 保证处理所有情况）、
而且支持值语义（可以放进 `vector` 而不需要 `unique_ptr`）。

## 七、回到 Part 0 提到的范式变迁

[00-01](../part0_overview/00-01_history.md) 里提过一个现象：
现代 C++ 的主流写法有"返璞归真"的趋势，
**过度使用虚函数的庞大类继承体系逐渐被摒弃**，
用泛型、函数式等范式开发精致的小类并良好组合成为大方向。

本章讲的就是这个趋势的技术依据：

- 虚函数有实质代价（对象变大、无法内联）
- 深继承体系让代码难以理解和测试
- 模板、CRTP、`variant`、`function` 提供了不需要继承的多态手段
- 组合比继承更灵活（见 [04-01](04-01_inheritance.md)）

但这**不是说虚函数不好**。它在它适用的场合（运行期多态、
异构容器、ABI 边界）仍然是最合适的工具。
变化的是"默认选择"—— 从"遇到多态就用虚函数"变成
"先想清楚是编译期还是运行期的多态"。

## 八、小结

| 要点 | 说明 |
|---|---|
| 虚函数的三项代价 | 对象多一个指针、调用多一次间接跳转、**无法内联** |
| 实测差距 | `-O2` 下约 4 倍（但含缓存局部性因素，不全是虚函数的锅）|
| 何时值得关心 | 函数体小 + 调用极频繁 + 阻止向量化；否则可以忽略 |
| 去虚化 | `final`、LTO、通过对象调用，都能让编译器消除虚调用 |
| CRTP | 基类模板以派生类为模板参数；`static_cast<Derived*>(this)` 调用具体实现 |
| CRTP 的独特能力 | 混入通用实现、每个派生类独立的静态成员、返回精确派生类型 |
| CRTP 的代价 | **无法异构容器**、代码膨胀、编译慢、错误难读、不能跨 ABI |
| 第三条路 | `std::function`（运行期）、`std::variant`（闭集合）、纯模板（鸭子类型）|
| 选择原则 | 运行期多态 → 虚函数；编译期多态 → 模板/CRTP；闭集合 → variant |

Part 4 到此结束。
